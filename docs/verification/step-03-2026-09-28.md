## Observations (outside scope, not affecting verdict)
- **Model misquoted the bank criteria.** In the live chat answer, the model wrote "BAJFINANCE (NBFC) and SBIN (BANK) met their group-specific criteria (ROA ≥2%, ROE ≥15% for NBFC/BANK)". The bank thresholds are actually ROA ≥1% and ROE ≥14%. `NumericClaimVerifier` did not catch this because 2% and 15% do appear in the evidence (as the NBFC thresholds). This is a good case for the Step 6 critic, or for a check that matches a threshold to its group.
- **End-to-end chat latency.** The chat took 252.8 s, almost all of it in the second model round (a 15,552-char tool result and 13,870 prompt tokens). The screen itself took milliseconds. A more compact tool result, such as the summary plus stocks meeting all criteria, with full tables on request, would cut the time. This matters for Step 4.
- **Data gaps.** 31 of the 46 screened stocks have at least one INSUFFICIENT_DATA result, mostly Revenue CAGR 3y DATA_CONFLICT, and the ROA/ROE of AXISBANK, HDFCBANK, ICICIBANK and SHRIRAMFIN are in DATA_CONFLICT. The screener handles this correctly, but the screen's coverage is thin.
- **Stocks outside the preset groups.** Stocks in INSURANCE, FINANCIAL_OTHER or UNKNOWN groups (4 in the live Nifty 50: BAJAJFINSV, HDFCLIFE, JIOFIN, SBILIFE) are listed as "Not screened" and get no per-rule results. This is visible and documented in the tool description. If you want insurers screened, add an `INSURANCE` rule set.
- **Deviations from the roadmap, not required by the spec.** Only `nifty50.csv` exists: there is no `niftynext50`/`midcap150` and no watchlist. Growth and cash-conversion spans are 3 years rather than 5, with the reason (four years of Yahoo statements) given at `application.yml:91-92`. `reasonable-value` uses an earnings-yield threshold rather than P/E vs its own 5y median. The roadmap allows this.
- **NBFC D/E is not blocked by the code.** `IndustryGroup.NBFC`'s non-primary set does not include `debtToEquityMultiple`, so a future NBFC rule on D/E would pass the construction guard. Only the current config and `ScreeningPresetsTest` keep it out.
- **Screening allowance lasts for the whole session.** `AiService.java:226` screens against `usage.evidence() + session.earlierEvidence()`. After one screen, a later answer in the same conversation keeps the "meets the supplied criterion" allowance in `UnsupportedClaimFilter`.
- **Edge case in the snapshot job.** In `SnapshotJob.capture`, an exception thrown by `repository.recordFailure` itself would escape the per-symbol catch and end the run as FAILED.
- **CSV parsing.** `Universes` splits CSV lines on `,` without handling quotes. The current file parses, but a company name containing a comma would stop startup.
- **Test logs mixed into the app log.** Test runs write to `logs/stock-research-ai.log`, for example "Snapshot run 1: TCS not captured: Yahoo down" from `SnapshotJobTest`, which mixes test noise with application logs.
- **Admin endpoints have no auth.** `/api/admin/snapshot` is unauthenticated, which is documented at `ScreeningController.java:24`. That's fine locally but needs protecting before any shared deployment.
- **CLAUDE.md edits.** `CLAUDE.md` was edited in the working tree to describe StockScreener as built.

## Learning check
1. **Why can't the LLM decide whether TCS "passes" ROCE ≥ 15%, and where is that decision made?**
   `StockScreener.evaluate` (`StockScreener.java:56-73`) decides it in Java with `Operator.holds` on a BigDecimal. The model only receives the rendered PASS/FAIL table from `screenStocks`. `ResearchInstructions` rule 5 and `UnsupportedClaimFilter` then limit it to reporting "meets / does not meet the supplied criterion". The tool description also forbids recalculating or re-ranking.
2. **How does a DATA_CONFLICT ROE of 40% against a 15% threshold come out, and why?**
   It comes out INSUFFICIENT_DATA. `evaluate` checks `metric.status() != VALID` before it compares anything, so the stored value is never looked at. `StockScreenerTest.aValueThatIsNotValidIsInsufficientDataNeverAPass` pins this down with exactly that 40% value. The renderer prints only "INSUFFICIENT_DATA" in the cell, and the ranking puts stocks with more INSUFFICIENT_DATA results lower.
3. **Why does a chat screen never call Yahoo, and how is the nightly job kept from getting rate-limited?**
   The `screenStocks` path is `ScreeningTools` → `ScreeningService` → `FundamentalsSnapshotRepository.latestCompletedRun` / `snapshots` → `StockScreener`, and none of these has a provider dependency. Yahoo is touched only by `SnapshotJob`, which runs weekdays at 18:30 Asia/Kolkata or on `POST /api/admin/snapshot`. It goes through `SnapshotBuilder` → `StockResearchService`, whose RestClients carry the shared `YahooRequestThrottle` interceptor (2 req/s), and it also pauses 1 s between companies. It allows only one run at a time (an `AtomicBoolean`), and screening reads only the newest run marked COMPLETED.
