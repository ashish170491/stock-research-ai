## Learning check
1. **Why does `ComparisonBuilder` never recompute a median, range or rank itself?** Because Step 13's `RatioContextService`/`FinancialCalculator`/`CalculationVerifier` already produced and verified those statistics per company in `ReportContext`; `ComparisonBuilder` only reads `ratio.peers().map(PeerContext::median)` (`ComparisonBuilder.java:66-67`). Recomputing it in the comparison layer would create a second, unverified source of the same number, breaking INV-6 ("every derived number is produced by `FinancialCalculator`... recorded so `CalculationVerifier` can reproduce it").
2. **Why is `ComparisonBuilder.build()` given `List<ComparisonTable.Gap>` as a separate parameter instead of putting a failed company straight into `List<ReportContext>`?** `ReportContext` has no "this company failed" state - it represents a company whose report was actually built. Keeping the gap list separate lets `ComparisonService` decide what "fetch failed" means (an exception message) while `ComparisonBuilder` only has to decide what to render for it (`"<symbol> could not be compared: <reason>"`, via `ComparisonRenderer.java:24-26`), and the two concerns (building the table vs. explaining a gap) stay in their own classes.
3. **Why does the narrative LLM call in `ComparisonService` pass `tableText` as both the user prompt and the verification evidence?** Because the rule is "the model only restates what Java already calculated and verified" - if the model were given the companies' full separate reports as evidence, `NumericClaimVerifier` would accept a figure quoted from one company's raw report even if that figure never made it into the aligned, NOT_COMPARABLE-checked table, defeating the point of alignment. Using `tableText` for both (`ComparisonService.java:96-100`) means a sentence can only survive if its figure is literally in the table the reader also sees.
