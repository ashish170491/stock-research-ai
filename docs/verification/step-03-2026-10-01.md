## Observations (outside scope, not affecting verdict)
- **Uncommitted engine changes.** Every result above holds for the working tree only. Commit the five-year-rules work, or re-verify, before relying on this verdict at a commit.
- **5-year rules depend on the filings.** In the live screen, 25 of the 46 screened stocks have at least one INSUFFICIENT_DATA result, for example `EICHERMOT ... Profit CAGR 5y (UNAVAILABLE)` and `ASIANPAINT ... Profit CAGR 5y (INVALID)`. With Yahoo's 4 years alone, every non-financial 5y rule is INSUFFICIENT_DATA (`ScreeningPipelineRegressionTest`). This is correct by INV-7, but it lowers how much the screen can say. A snapshot taken before this change has no 5y rows, so screening an older run makes every 5y rule INSUFFICIENT_DATA.
- **The closing-equity check is a heuristic.** `SnapshotCalculator.onAverageEquity` decides the basis from `formula == AVERAGE_BALANCE_RETURN_PERCENT && inputs().size() == 3`. It works today, but a change to the ROE inputs would silently make every ROE average UNAVAILABLE (that errs safe). An explicit basis flag on the data point would be sturdier.
- **The live app is slightly behind the tree.** `ScreeningView.java` changed at 21:01, after the app started at 20:56, so `/api/screening/data` (the web page) in the running app doesn't have the new VALID/status cell logic. Restart before checking the UI.
- **The tool description doesn't mention spans.** `screenStocks`'s description doesn't say that growth is measured over 5 fiscal years and ROE/OCF over 3. The rendered table headers do say it.
- **`CriteriaValidator.spansNotApplied`** (Step 4 scope) avoids a duplicate note by matching the text `years + "-year span"` against earlier notes. That breaks silently if the wording changes.
- **Carried over from 2026-09-29, not re-checked:** admin endpoints have no auth; `Universes` CSV parsing ignores quotes; an exception from `repository.recordFailure` escapes the per-symbol catch; the test JVM shares the app's rolling log file.

## Learning check
1. **A company has six fiscal years of filings but FY23's net profit is a DATA_CONFLICT. What does `Profit CAGR 5y ≥ 10%` give, and where is that decided?**
   `SnapshotCalculator.cagr(annual, 5, ...)` takes the window FY21-FY26 and runs `blocked(...)` over every year of it, not only the two ends. The disputed middle year passes its DATA_CONFLICT status on to the CAGR, which gets no value. `StockScreener.evaluate` (line 57) then returns INSUFFICIENT_DATA before `Operator.holds` runs, so the rule is never PASS and never FAIL. The model only quotes the "Not assessed" column.
2. **Why can't `quality-compounder` be given an OCF/PAT 5y rule for banks, even though the metric now exists?**
   `ScreeningMetric.OCF_TO_PAT_5Y_MULTIPLE` has sector key `ocfToPat5yMultiple`, and it is in `IndustryGroup.BANK`'s non-primary set (`IndustryGroup.java:23`). The `ScreeningCriteria` constructor (lines 64-70) throws "not a primary metric for BANK", so `ScreeningPresets` fails at startup. `ScreeningPresetsTest` asserts this metric is absent from every BANK/NBFC rule set.
3. **Why does a screen in chat cost milliseconds and no Yahoo or NSE calls, while the nightly run takes about 200 s?**
   Screening reads only H2: `ScreeningService` → `FundamentalsSnapshotRepository.latestCompletedRun/snapshots` → `StockScreener`, none of which holds a provider. Only `SnapshotJob` (18:30 Asia/Kolkata on weekdays, or `POST /api/admin/snapshot`) calls `SnapshotBuilder` → the research layer, which reaches Yahoo and the filings. It is throttled by a 1 s pause between companies plus the provider throttles, runs one at a time, and records a per-symbol failure without stopping. Live: run 12 took 197 s, then screens took 2-7 ms with zero Yahoo log lines.
