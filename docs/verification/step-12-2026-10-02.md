2. **New, caused by the hyphen fix: "Nifty-100" is now quietly read as no index.** `UNIVERSE_NUMBER` now accepts `nifty[\s-]*`, but `OTHER_UNIVERSE` (`CriteriaValidator.java:62-65`) still uses `nifty\s*`. My probe on "Which Nifty-100 stocks have ROE above 20%?" screened the Nifty 50 with the reading "the default when a request names no index that can be screened", and with no Not-applied note. Before the fix this request was refused, which was safe. "Nifty 100" with a space still gets the note. The universe in use is still shown, so this is not a model choice, but the reading is inaccurate. Fix: use `[\s-]*` in `OTHER_UNIVERSE` too, and add "Nifty-100" to `CriteriaValidatorTest`.
3. **In the tool path the universe is a model argument.** It is limited to the Nifty 50, and a NIFTY500 argument is refused. If the router ever sent a Nifty 500 screen to SPECIFIC_QUESTION, the model could call `screenStocks` with no universe. The router's `SCREEN` pattern (`RequestRouter.java:84-91`) catches the usual phrasings, so the risk is small.
4. **The weekday nightly job now covers 550 companies.** `SnapshotJob.nightly` (`:66-72`) iterates every universe. Run 13 took about 71 minutes for the 500, with filings mostly already stored for the Nifty 50. Later runs should be faster, because filings are stored once.
5. **Run counts during a run.** `run.stored` and `run.failed` read 0 until `finishRun`. `index.html:654` now shows "(N stored so far)" from `filedYears.stored` while a run is in progress, which covers the page. API readers should use `filedYears.stored`.
6. **REIT and trade-for-trade members.** BIRET (a REIT) was stored with no profile, so it shows as UNKNOWN under Not screened. The other two REITs failed the own-listing check. 36 stocks were not screened in the live quality-compounder run, because their group has no rules or is unknown.
7. **What counts as a filed year.** `filedFiscalYears` counts a year with any `OFFICIAL_FILING` point, whatever its DataStatus, so the 62.2% is an upper bound on usable filed years.
8. **The two failures are what the guard is for.** `EMBASSY` resolving to `EMBDL` (Embassy Developments, a different company) is the real-world case the own-listing check was written for. Without it, a REIT would have been stored with a property developer's figures.

## Learning check
1. **Who decides whether a request is screened on the Nifty 50 or the Nifty 500, and why can't the model change it?** Java does, in `CriteriaValidator.universe(...)` (`CriteriaValidator.java:172-199`), from the user's raw message (`AiService.java:196` → `ScreenerAgent.java:197`). The model's `.entity(ExtractedCriteria.class)` output has no universe field. In the live run it returned only `preset: quality-compounder`, and Java still read "Nifty 500" from the words.
2. **Why does `screenStocks` refuse the Nifty 500, and how does the answer stay verifiable?** A table of about 500 rows (`n500-screen.md` is 129 KB) would fill qwen3:8b's context. The tool returns a short `UNKNOWN_UNIVERSE` text without calling the service (`ScreeningTools.java:66-71`), and still records the call on `ToolUsage` (`:78`). The answer checks can then see that no table was returned.
3. **What stops a placeholder or mis-resolved constituent from being stored under a member?** There are two layers. `Universes.load` skips the `DUM...` ISIN row (`Universes.java:58-60`). For a real member whose symbol resolves elsewhere through the resolver's fallbacks (`YahooSymbolResolver.java:105-110`), `SnapshotBuilder.ownListing` (`:97-106`) throws before a snapshot exists, and `SnapshotJob` records it as a failure (`:127-131`). Live, EMBASSY resolved to EMBDL and was rejected.
