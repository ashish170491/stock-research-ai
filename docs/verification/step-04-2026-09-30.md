The code uses `.entity(ExtractedCriteria.class)` and builds `ScreeningCriteria` in stage 2. This is arguably the better design. Consider changing the S4-2 wording in `docs/specs/step-04-screener-agent.md` (in a separate commit) so the spec matches the implementation.
2. **INV-3 script heuristic.** `scripts/verify-invariants.sh` passes any file that names `NumericClaimVerifier`, even only in Javadoc. `ScreenerAgent` and `AiService` now name it only in Javadoc and call `AnswerChecks`. Both are correct today, but the script would not catch a class that only mentions the verifier. A stronger check would also accept `AnswerChecks` and ignore comment lines.
3. In stage 4, the `ResponseStatusException` that `OllamaCalls` throws when Ollama is unreachable is caught by `catch (RuntimeException)` (`ScreenerAgent.java:214`). The user gets the table with `NO_SUMMARY` instead of a 503. This is intended and tested.

5. Only NIFTY50 can be screened. Requests that name other universes are reported under "Not applied" (`CriteriaValidator.java:108-112`), and the screen runs on the Nifty 50 anyway.
6. CLAUDE.md has uncommitted rule additions for ScreenerAgent and ScreeningCountVerifier, and there is a new `src/test/resources/logback-test.xml`. Both should be committed together with the step.
7. `RequestRouter` now asks `NseSymbolDirectory.namedIn` before taking the SCREEN route by keyword. This fixes the Reliance misrouting that the earlier run of this report noted. ## Learning check
1. **Why does stage 1 bind to `ExtractedCriteria` (all strings) and not straight to `ScreeningCriteria`, and what does Java check afterwards?** Suppose the model writes `PROMOTER_HOLDING` or `"18%"`. Binding to enums or `BigDecimal` would throw inside `.entity(...)`, and the user would never learn why. With strings, every value reaches `CriteriaValidator`. It checks the metric against the `ScreeningMetric` whitelist (`CriteriaValidator.java:329-336`) and the threshold against `withinBounds` (`:337-345`). It also checks that the threshold is a number the user actually wrote, which catches 18 converted to 0.18 (`:311-326`). Each problem becomes a "Not applied" note the user sees. That is the chain idea: the LLM produces structure, and Java decides what is valid.
2. **How do two separate ChatClient calls end up in one conversation trace?** `ChainTracer.start` opens a `TraceContext` on the thread and logs `USER >` (`ChainTracer.java:45-53`). Both clients carry the same `ConversationTraceAdvisor` (`ScreenerAgent.java:140`, `:145`). When `adviseCall` finds a trace already open, it logs "model call N" inside it (`withinChain`) and does not start a new trace. The try-with-resources `close()` logs `DONE ... | 2 model call(s)` and ends the context.
3. **Why does the stage-4 summary model see `renderSummary` and not the table, and what catches it if it still gets a figure or count wrong?** The model gets only the counts the application made (`ScreeningRenderer.renderSummary`), so it has nothing to tally or re-rank. The prompt tells it to copy counts. `AnswerChecks` then checks the draft against the full rendered result. `NumericClaimVerifier` checks figures. `ScreeningCountVerifier` checks the small whole-number counts that NumericClaimVerifier deliberately skips. `UnsupportedClaimFilter` removes judgements such as "quality company". Each removal adds a visible note (`AnswerChecks.java:36-57`, tested in `ScreenerAgentTest.java:219-234`). Thinking is off on this client (`ScreenerAgent.java:144`) because copying counts needs no reasoning, and thinking is most of the latency.
