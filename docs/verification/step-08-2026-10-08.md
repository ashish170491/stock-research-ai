## Learning check
Three questions the developer should be able to answer about this step's Spring AI concepts, answered from THIS codebase:

1. **Why does the planner `ChatClient` never need `.defaultTools(...)`, and how is that enforced rather than just hoped for?**
   The planner's only job is to turn a goal into `ResearchPlan` JSON via `.entity(ResearchPlan.class)` (`ResearchOrchestrator.java:110`) - every step it describes is *executed* afterwards by Java's own `executeStep` switch, which calls `screenerAgent.answer`, `comparisonService.compare`, etc. directly (`ResearchOrchestrator.java:174-204`). Giving the planner tools would be pointless (it never gets a second turn to see a tool's result before producing its one JSON object) and would violate S8-2. This isn't just a comment: `ResearchOrchestratorTest.thePlannerIsGivenNoTools` (lines 124-139) inspects the actual `Prompt` sent to the model and asserts `ToolCallingChatOptions.getToolCallbacks()` is null or empty - a real assertion against Spring AI's request object, not a design note.

2. **How does `ChainTracer.Chain.modelCalls()` correctly count a step's model calls when the orchestrator itself never calls the sub-component's model directly (e.g. `ScreenerAgent.answer` makes its own 2 calls)?**
   `ResearchOrchestrator` opens one `ChainTracer.Chain` for the whole plan (`tracer.start("orchestrator", goal)`, `ResearchOrchestrator.java:107`). Spring AI's `ConversationTraceAdvisor` runs on every `ChatClient` in the app (including `ScreenerAgent`'s own clients), and because each component also calls `tracer.start(...)` internally, `ChainTracer`'s thread-local `TraceContext` means those nested calls become **non-owning children** that reuse the *same* `ConversationTrace` rather than starting a fresh one. So `chain.modelCalls()` (the new accessor, `ChainTracer.java:60-63`, delegating to the pre-existing package-private `ConversationTrace.modelCalls()`) accurately reflects every model call any step's internals made, without the orchestrator needing to know what's inside `ScreenerAgent` or `ComparisonService`. The live run demonstrated this directly: the SCREEN step alone made 2 calls (extraction + summary) that `ScreenerAgent` itself issued, and the orchestrator's own budget and trace line (`"stage 2 SCREEN > 18494 ms, 2 model call(s)"`) picked them up correctly without any explicit counting code inside `ScreenerAgent`.

3. **Why does a SCREEN step always pause the whole plan, even if SCREEN appears in the middle rather than first - and why is that a reasonable generalization rather than a deviation from S8-4's wording ("after the screening step")?**
   `execute()`'s loop checks `if (step.type() == StepType.SCREEN)` unconditionally after running *any* SCREEN step (`ResearchOrchestrator.java:165-169`), not just one at position 0. S8-4 says "after the screening step, return the shortlist and wait" without restricting SCREEN to the first position - and `PlanValidator` already requires any SCREEN step to be the one later DEEP_DIVE/COMPARE steps draw their shortlist from, so a human reviewing *any* shortlist before it drives further (potentially expensive) deep dives or comparisons is exactly the checkpoint's purpose, regardless of where in the plan it occurs. The live run's own plan (`SCREEN, DEEP_DIVE, COMPARE, WRITE_MEMO`) only exercised the common case (SCREEN first), so this generalization is judged reasonable by design but not itself exercised by a plan with SCREEN in a later position in this verification pass - a plan like `[DEEP_DIVE(explicit symbols), SCREEN, WRITE_MEMO]` would be a good addition to `ResearchOrchestratorTest` to pin down the generalization explicitly, but no test or live behavior contradicts it.
