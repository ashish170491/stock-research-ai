## Summary
All automated tests pass (800/800, confirmed from `target/surefire-reports`), all `AUTO` invariants pass, and the live three-turn script (`Research Infosys` -> `how has it performed over 5 years?` -> `and its debt?`) resolves all three turns to INFY on a single conversationId, with a second, fresh conversationId correctly having no memory of it. The one substantive finding: the tool-loop and general `ChatClient`s do **not** use `MessageChatMemoryAdvisor` as S1-2 and S1-3 literally require. Memory is instead managed by hand in `AiService` (`chatMemory.get(conversationId)` / `chatMemory.add(conversationId, ...)`), a choice recorded in the original commit message (`1540897`, "Memory is managed in AiService rather than by MessageChatMemoryAdvisor, which saves the draft before the verifiers run") and still implicit in `AiService.chat()`'s Javadoc today ("What is remembered is what the user was shown - the screened answer, never the model's draft"). This is not the literal implementation named by the spec, but it is deliberate, it achieves every behavioural goal the criteria care about (bounded window, no shared default conversation, per-conversation isolation, memory never bypassing verification), and - importantly - using `MessageChatMemoryAdvisor` as a `CallAdvisor` would store the model's *unverified draft* before `AiService`'s own post-call screening runs, which would directly break S1-7 and INV-3's "verification isn't weakened" requirement. I could not decide this alone, since it is a question of whether the spec's exact wording or its intent governs; I mark S1-2, S1-3 and the dependent S1-8 as **NEEDS_REVIEW** rather than FAIL or PASS, and recommend accepting the substitution (see per-criterion reasoning below) but leave the call to a human.

## Learning check
1. **Why does `AiService` build the two `ChatClient`s with `.defaultAdvisors(conversationTraceAdvisor)` but no memory advisor, and pass `chatMemory.get(conversationId)` as `.messages(history)` by hand instead?** Because `MessageChatMemoryAdvisor` would add the model's raw response to memory as part of the advisor chain, before `AiService`'s own post-call code (`AnswerChecks`/`NumericClaimVerifier`/`UnsupportedClaimFilter`) gets to remove unsupported claims from it. Doing memory by hand lets `remember()` be called only after `screened()` has produced the final, checked text, so nothing enters memory except what the user was actually shown.
2. **Why is "a figure repeated from an earlier turn" checked against `session.earlierEvidence()` rather than against the conversation's chat history text?** Because chat history (`chatMemory`) only ever contains text that already passed verification in its own turn - checking against it again would be redundant and, if it ever did contain something ungrounded, would let that ungrounded figure "launder" itself into legitimacy just by having been said once. Checking against the recorded tool evidence (`ToolUsage.evidence()` this turn, `ResearchSession.earlierEvidence()` for up to 5 earlier turns) means a figure is accepted only because real tool output backs it, not because it was said before.
3. **Why does a brand-new `conversationId` asking "and its debt?" get `NAME_THE_COMPANY` instead of an error or a guess?** `RequestRouter.needsACompany` (checked in `AiService.chat` before the tool loop runs) is true exactly when the intent is `SPECIFIC_QUESTION`, the message itself names no company, the message's wording refers back to one ("its", "and...", etc.), *and* the session has no earlier company either. Routing deliberately never guesses a company the user didn't name and the conversation didn't establish; it asks instead, which is also why this path is cheap (no tool call, no model call for the tool loop) and immediately remembered so a one-word reply ("Infosys") is understood as the answer to that question.
