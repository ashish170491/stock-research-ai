## Learning check
1. **Why does moving the cache TTLs from a hardcoded `Map` in `YahooCacheConfiguration` to `YahooFinanceProperties.Cache` change nothing about `YahooCacheConfigurationTest`'s assertions, only how the values reach the test?** The test (`YahooCacheConfigurationTest.givesEachCacheItsOwnTimeToLive`) always asserted against the Caffeine cache's actual `expireAfterWrite()` policy, not against the Java constant directly - so swapping the TTL source from a static map to a `@ConfigurationProperties` record only changes how the test constructs its input (`YahooFinanceProperties.Cache(...)` instead of nothing), not what it checks.
2. **Why is it safe to wrap `RequestRouter.byModel()`'s and `LlmSymbolResolver.resolveTickerGuess()`'s model calls in `ollama.call(...)` without changing their existing `catch (RuntimeException ex)` fallback behaviour?** `OllamaCalls.call()` only intercepts `ResourceAccessException` and rethrows it as a `ResponseStatusException` - itself a `RuntimeException` - so each caller's pre-existing broad catch still fires exactly as before (routing falls back to `SPECIFIC_QUESTION`, the resolver returns `Optional.empty()`); the only change is that the *message* an unreachable Ollama produces is now the same everywhere, rather than diverging per call site.
3. **Given S0-L2's 49.5s-101.3s spread on an identical, fully-cached "fundamental overview of TCS" prompt, what does the near-zero S0-L3 data-fetch time tell you about where that variance comes from?** Since none of the three repeats re-fetched profile/financials/history and only the first re-fetched valuation (its 5-minute TTL having just expired), essentially all of the measured wall-clock time in each run is the single model round-trip over the same ~9190-token prompt - so the 2x spread is inference-time variance on this machine/model, not caching or I/O, and tuning the interpretation `ChatClient`'s prompt size or `OllamaChatOptions` (not the cache layer) is where to look if the 60s budget needs to be met more reliably.
