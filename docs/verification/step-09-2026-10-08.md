Design choice flagged by the author, reviewed here:
- **S9-2 bean shape.** `McpToolsConfiguration.researchMcpTools` returns `List<McpServerFeatures.SyncToolSpecification>`,
  not a `ToolCallbackProvider`/`ToolCallback`-typed bean. I independently decompiled the actual Spring AI
  2.0.1 jars (not just read the comment) to check the claimed circular dependency is real, not a
  post-hoc excuse:
  - `McpServerAutoConfiguration.mcpSyncServer(...)` (decompiled from
    `spring-ai-autoconfigure-mcp-server-common-2.0.1.jar`) takes exactly
    `ObjectProvider<List<McpServerFeatures.SyncToolSpecification>>` as one of its parameters - this is
    the real wiring point the bean must match, and it does.
  - `ToolCallingAutoConfiguration.toolCallbackResolver(...)` (decompiled from
    `spring-ai-autoconfigure-model-tool-2.0.1.jar`) sweeps every `ToolCallbackProvider` bean in the
    context into a `StaticToolCallbackResolver`, used by the app's own default `ToolCallingManager`
    (a dependency of `ollamaChatModel`). Its filter, `isMcpToolCallbackProvider`, only excludes beans whose
    runtime type is exactly `org.springframework.ai.mcp.SyncMcpToolCallbackProvider` or
    `AsyncMcpToolCallbackProvider` (the MCP-*client*-side providers, for consuming someone else's MCP
    server) - **not** `MethodToolCallbackProvider` (the type used here to wrap local `@Tool` beans for
    exposure). So a `MethodToolCallbackProvider`-typed bean genuinely would be swept in.
  - `LlmSymbolResolver(ChatClient.Builder chatClientBuilder, OllamaCalls ollama)` (confirmed at
    `LlmSymbolResolver.java:35`) really does need `ChatClient.Builder`, which Spring AI's own
    autoconfiguration builds from `ollamaChatModel`. Sweeping a bean that transitively constructs
    `StockPriceTool -> ... -> LlmSymbolResolver -> ChatClient.Builder` into `ollamaChatModel`'s own
    dependency chain is exactly a bean-graph cycle.
  - Conclusion: the circular-dependency claim is correct, not speculative, and the fix (returning the
    already-converted `List<SyncToolSpecification>`, matching the exact autoconfiguration hook) is the
    narrowest fix that avoids it. **Judged an acceptable, well-justified deviation from S9-2's literal
    wording**: the criterion's substance - "tools are exposed through [use of] a tool-callback provider" -
    is satisfied (the bean is built via `MethodToolCallbackProvider.builder()...build()` internally,
    `McpToolsConfiguration.java:38-41`), and the testable outcome (the six named tools, reachable from an
    MCP client) is independently confirmed live, below. This is not graded as a FAIL.

## Learning check
Three questions the developer should be able to answer about this step's Spring AI concepts, answered from THIS codebase:

1. **Why is `McpToolsConfiguration.researchMcpTools` typed `List<McpServerFeatures.SyncToolSpecification>` instead of returning a `ToolCallbackProvider` bean directly?**
   Because `McpServerAutoConfiguration.mcpSyncServer(...)` consumes exactly `ObjectProvider<List<SyncToolSpecification>>` (confirmed by decompiling the autoconfiguration class), and because Spring AI's `ToolCallingAutoConfiguration.toolCallbackResolver()` sweeps *every* `ToolCallbackProvider` bean in the context (except the two MCP-client-specific classes `SyncMcpToolCallbackProvider`/`AsyncMcpToolCallbackProvider`) into the resolver backing the app's own default `ToolCallingManager`, a dependency of `ollamaChatModel`. Since one of the four tools (`StockPriceTool`, via `StockMarketDataService -> YahooFinanceMarketDataProvider -> YahooSymbolResolver -> LlmSymbolResolver`) itself needs `ChatClient.Builder` (built from `ollamaChatModel`), registering a `MethodToolCallbackProvider`-typed bean would create a real bean-graph cycle. Converting to the plain list sidesteps the sweep entirely while still being picked up by the exact autoconfiguration hook MCP needs.

2. **Why does an MCP tool invocation never need to supply a `ToolContext`, and why doesn't that break `ToolUsage` recording?**
   `ToolUsage` exists to let `AiService`'s chat path check which tools were used and with what evidence, scoped to one request via Spring AI's `ToolContext` map (`ToolUsage.asToolContext()`/`CONTEXT_KEY`). MCP tool calls come in through `MethodToolCallback.call(String)` (the single-arg overload, used when there is no application-level `ToolContext` to pass), which internally calls `call(String, null)`. `ToolUsage.record(ToolContext, Call)` explicitly null-checks `context != null && ...` before touching anything, so this is a safe no-op rather than a `NullPointerException` - there is simply no per-request `ToolUsage` to record onto when a tool is reached directly by an external MCP client instead of the chat flow.

3. **Which tool classes are exposed over MCP, and which are deliberately not restricted to only the six S9-2-named tools?**
   All four tool beans that already exist for the chat agent - `StockPriceTool`, `StockResearchTools`, `ScreeningTools`, `DocumentSearchTools` - are passed into one `MethodToolCallbackProvider`, so every `@Tool` method on them (8 total: the six named in S9-2, plus `getShareholding` and `searchCompanyDocuments`) is exposed, not a hand-picked subset. This matches the roadmap's intent ("Claude Desktop or Claude Code can call `screenStocks`, `getFinancialSummary` and the other tools directly") rather than S9-2's "at least" list being read as an exhaustive allow-list.
